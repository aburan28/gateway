## [HIGH] Predictable, low-entropy serial numbers for self-signed CA and Envoy leaf certificates
**File:** /home/user/gateway/internal/crypto/certgen.go:272-274 (and call sites at lines 205, 243)
**Description:** `newSerial(now)` returns `big.NewInt(int64(now.Nanosecond()))`. `time.Time.Nanosecond()` only returns the nanosecond fraction within the current second (range 0..999_999_999, ~30 bits). All control-plane / data-plane certs (CA, Envoy Gateway server cert, Envoy server cert, Envoy rate-limit cert) are issued with a serial in that small range. Because the CA cert and both leaf certs in a single `GenerateCerts` call are minted within microseconds of each other, all three serials are clustered, and the CA serial often collides with a leaf serial. RFC 5280 §4.1.2.2 and the CA/Browser Forum baseline require serial numbers to contain at least 64 bits of CSPRNG output to prevent collision attacks (CVE-2008-0166 class). Implications:
- Two CAs generated by separate `envoy-gateway certgen` runs have a non-trivial collision probability for serial numbers (~birthday paradox over 10^9), and intra-CA serial collisions across leaves are possible.
- Predictable serials weaken protections against chosen-prefix collision attacks on the cert signature.
**Recommendation:** Use `crypto/rand` to generate a 128-bit serial, e.g. `serial, err := rand.Int(rand.Reader, new(big.Int).Lsh(big.NewInt(1), 128))`. Reject `0` and ensure positive.

## [HIGH] Generated TLS private keys and OIDC HMAC secret written world-readable (host mode)
**File:** /home/user/gateway/internal/utils/file/file.go:16 (mode `0o644`) — consumed by /home/user/gateway/internal/cmd/certgen.go:181-209 and /home/user/gateway/internal/infrastructure/host/infra.go:163-178
**Description:** `file.Write` creates files with permission `0o644`, and `file.WriteDir` creates the parent directory with `0o755` (and `infra.go:163` uses `0o750` for `MkdirAll`, but the inner files are still 0644). All control-plane TLS private keys (`tls.key` for envoy-gateway, envoy, envoy-rate-limit) and the OIDC `hmac-secret` are emitted via these helpers in host-mode (`certgen --local`, and the auto-generation path in `maybeGenerateCertificates`). On a shared host, any local user can read the Envoy/EG private keys and the OIDC HMAC seed (which is used to sign session cookies). Note that the Kubernetes path (Secret objects) is unaffected; this is only host mode.
**Recommendation:** When writing private keys / HMAC material, open with `0o600` and ensure parent directory is `0o700`. Either change `file.Write` to take a perm argument, or add a dedicated `WriteSecret(data, path)` helper used by certgen / `maybeGenerateCertificates`. Compare to the test files which already correctly use `0o600` (e.g. `internal/gatewayapi/runner/runner_test.go:265-268`).

## [MEDIUM] Self-signed leaf certificates missing ExtKeyUsage (ServerAuth/ClientAuth)
**File:** /home/user/gateway/internal/crypto/certgen.go:204-217 (leaf template) and 244-256 (CA template)
**Description:** The leaf cert template only sets `KeyUsage` (`DigitalSignature | DataEncipherment | KeyEncipherment | ContentCommitment`) — no `ExtKeyUsage` is set. RFC 5280 §4.2.1.12 and modern verifiers (Chromium, BoringSSL, recent Go) increasingly require an `ExtKeyUsageServerAuth`/`ClientAuth` EKU on leaves. The CA also omits EKU, which is the conservative choice (CA EKU is constraining), so that part is fine, but the leaves should set EKU explicitly. Additionally the `KeyUsage` set is overly broad — `ContentCommitment` (nonRepudiation) is not appropriate for TLS server certs and should be removed. Same cert is used both as server cert and client cert (e.g. Envoy connects to xDS), so both `ExtKeyUsageServerAuth` and `ExtKeyUsageClientAuth` are likely needed.
**Recommendation:** Set `ExtKeyUsage: []x509.ExtKeyUsage{x509.ExtKeyUsageServerAuth, x509.ExtKeyUsageClientAuth}` on the leaf template and drop `KeyUsageContentCommitment` and `KeyUsageDataEncipherment` (the latter is meaningless for TLS 1.2+ AEAD ciphers).

## [MEDIUM] JWKS / OIDC discovery clusters do not enable SAN validation
**File:** /home/user/gateway/internal/xds/translator/jwt.go:242-269 (`buildXdsUpstreamTLSSocket`), used by /home/user/gateway/internal/xds/translator/oidc.go:498 and /home/user/gateway/internal/xds/translator/utils.go:203
**Description:** `buildXdsUpstreamTLSSocket` builds an Envoy `UpstreamTlsContext` for OIDC / JWKS / OAuth remote endpoints. It sets `Sni: sni` and a `TrustedCa` (system trust store), but does NOT set `AutoSniSanValidation = true` and does NOT populate `MatchTypedSubjectAltNames`. Envoy does not implicitly enforce that the server certificate's SAN matches the SNI just because SNI is set; it only verifies the cert chain against the trust store. As a result, any TLS server presenting a publicly-trusted cert (for any hostname) can impersonate a JWKS endpoint or OIDC discovery endpoint. An attacker with the ability to redirect DNS or BGP, or a malicious DNS resolver, can swap the JWKS or OIDC provider for one they control and forge JWTs. Compare with `buildXdsUpstreamTLSSocketWthCert` (translator.go:1245-1304) which correctly enables `AutoSniSanValidation`.
**Recommendation:** In `buildXdsUpstreamTLSSocket` add `AutoSniSanValidation: true` to the `UpstreamTlsContext`, or build a `CombinedValidationContext` with a `MatchTypedSubjectAltNames` matcher for the SNI hostname (mirroring the logic in `buildValidationContext` at translator.go:1188-1243).

## [LOW] `discoverEndpointsFromIssuer` uses `TLSUpstreamConfig.ToTLSConfig` which silently honors `InsecureSkipVerify`
**File:** /home/user/gateway/internal/ir/xds.go:3220-3246 (`ToTLSConfig`), called from /home/user/gateway/internal/gatewayapi/securitypolicy.go:1600
**Description:** `ToTLSConfig` copies `t.InsecureSkipVerify` straight into `tls.Config.InsecureSkipVerify` and `MinVersion` is only set when explicitly configured. If a SecurityPolicy's OIDC provider has its `BackendTLS.InsecureSkipVerify=true` set (e.g. via a Backend resource), the control-plane Envoy Gateway process itself fetches the `/.well-known/openid-configuration` over an unverified TLS connection. That document subsequently dictates token/authorization endpoints — full takeover of the OIDC flow. The flag is admin-controlled, but the result is that an OIDC provider becomes spoofable from any on-path MITM. Note this is the control-plane Go HTTP client, distinct from the dataplane Envoy.
**Recommendation:** In `ToTLSConfig`, default `MinVersion = tls.VersionTLS12` (or 1.3) when unset; emit a control-plane log warning when `InsecureSkipVerify` is true so operators see it; consider refusing `InsecureSkipVerify` for OIDC discovery specifically — its only purpose is to bootstrap trust.

## [LOW] `crypto.LoadTLSConfig` calls underlying loader twice (TOCTOU window) and uses `os.ReadFile` for the CA without `Lstat` checks
**File:** /home/user/gateway/internal/crypto/cert_load.go:17-57
**Description:** `LoadTLSConfig` calls `loadConfig()` once eagerly (line 45) and then again via `GetConfigForClient` on each handshake (line 53). Between the early load and the runtime load, the cert/key/ca files may change (rotation), so the validity check at startup is best-effort. More importantly, `os.ReadFile(caCrt)` and `tls.LoadX509KeyPair(tlsCrt, tlsKey)` follow symlinks (no `Lstat`/`O_NOFOLLOW`), so a writable parent directory or symlink swap could redirect the loader at runtime. Paths are admin-supplied (defaults `/certs/tls.crt`, etc.), so the practical impact is limited unless the cert directory is writable by a non-root user. Worth noting because `GetConfigForClient` re-reads on every handshake — high frequency increases attack surface for symlink races.
**Recommendation:** Open cert/key/CA via `os.OpenFile` with `O_NOFOLLOW`, then `io.ReadAll`. Cache the parsed `tls.Config.Certificates` and only rotate when a `fsnotify` watcher fires or a file checksum changes, rather than re-reading on every handshake. Also document that the cert directory must be `0700` and owned by the EG service account.

## [LOW] `math/rand` seeded from wall clock used for picking `MaxConnectionAge`
**File:** /home/user/gateway/internal/xds/runner/runner.go:142-145
**Description:** `getRandomMaxConnectionAge` uses `rand.New(rand.NewSource(time.Now().UnixNano()))` to pick one of three `MaxConnectionAge` durations for the xDS gRPC server. Not a security primitive (no key material, no session ID), and the gosec annotation acknowledges this. The only risk is that multiple xDS replicas booting at the same nanosecond pick the same age, partially defeating load spreading. The `//nolint:gosec` is appropriate. Flagged for visibility only.
**Recommendation:** Optional: switch to `crypto/rand` (`rand.Int`) — overhead is negligible and removes the gosec exception. No security action required.

## [INFO] SHA-1 usage is bounded to non-security contexts
**File:** /home/user/gateway/internal/crypto/certgen.go:284-288 (`bigIntHash` → SubjectKeyId per RFC 5280); /home/user/gateway/internal/gatewayapi/securitypolicy.go:1838-1840 (htpasswd `{SHA}` format size check)
**Description:** Two SHA-1 usages were found in production code paths. `bigIntHash` derives a `SubjectKeyId` from the RSA modulus — RFC 5280 §4.2.1.2 explicitly endorses SHA-1 for this purpose and the comment in code calls this out. The htpasswd validator only checks that `{SHA}<base64>` decodes to exactly 20 bytes; Envoy itself is the consumer of the digest, and only the format is validated client-side. Both are acceptable.
**Recommendation:** None. Keep the `//nolint:gosec` annotations and explanatory comments.

## [INFO] Certificate validity is 5 years (DefaultCertificateLifetime)
**File:** /home/user/gateway/internal/crypto/certgen.go:31-32
**Description:** Self-signed CA and leaves are issued with NotAfter = now + 5 years. CA/B Forum baseline limits public TLS to 398 days; for an internal self-signed CA the 5-year horizon is unusual but not abusive. There is no rotation mechanism shipped — operators must re-run `certgen --overwrite` manually. The OIDC HMAC secret is generated alongside and never auto-rotated either, which the code comments acknowledge ("We need to rotate the HMAC secret in the future" — securitypolicy.go:1345-1346). Flag for visibility; the 5-year lifetime is a design choice, but combined with no rotation it means compromise of these keys is durable.
**Recommendation:** Document the rotation procedure in operator docs; consider shortening default to 1-2 years; surface a CronJob example for re-running `certgen`.

## Reviewed, no issues

- **`crypto/rand` correctness** — every key/serial generation in scope uses `crypto/rand.Reader` (certgen.go:198, 218, 237, 257, 307; provider/file/store.go:365). No `math/rand` for key/serial/session material.
- **TLS MinVersion in control plane** — both `cert_load.go:40` and `cert_load.go:50` pin `tls.VersionTLS13`. Listener defaults via `clienttrafficpolicy.go:812` pin TLS 1.2 minimum for dataplane.
- **TLS InsecureSkipVerify in production code** — restricted to (a) user-opted `wasm/httpfetcher.go` and `wasm/imagefetcher.go` "insecure mode" flags, (b) IR-level field that must be explicitly enabled via Backend CRD (CEL-validated to forbid combining with CA refs at `api/v1alpha1/backend_types.go:175`). No silent default true.
- **Cross-namespace secret refs (SDS / TLS)** — `validateSecretRef` (validate.go:881) and `validateTerminateModeAndGetTLSSecrets` (validate.go:368) both enforce ReferenceGrants. All in-tree callers of `validateSecretRef` pass `allowCrossNamespace=false`, which is even stricter than ReferenceGrant. `backendtlspolicy.go:getCaCertsFromCARefs` (line 478) only reads from the policy's own namespace because the API uses `LocalObjectReference`. `ClusterTrustBundle` is cluster-scoped by design.
- **Weak crypto primitives in security paths** — no MD5/DES/RC4/ECB usage; no hardcoded IVs; no predictable nonces. SHA-1 only in the two acceptable contexts noted above.
- **RSA key size / EC curve** — RSA 2048 (`certgen.go:36`) meets NIST recommendation. No ECDSA generation in scope.
- **PEM/x509 unbounded parsing** — `filterValidCertificates` (tls.go:181-249) iterates `pem.Decode` over bounded secret data; `parseCertsFromTLSSecretsData` walks bounded input. No nested-cert-chain expansion that could amplify memory.
- **Cert validity window enforcement** — `filterValidCertificates` (tls.go:212-221) and `validateCrl` (tls.go:252-269) compare `time.Now()` against NotBefore/NotAfter and CRL `NextUpdate`/`ThisUpdate`. No bypasses.
- **Secret material in logs** — searched control-plane log/error sites; only metadata (`"loaded TLS certificate and key"`) is logged; raw secrets/keys not logged or returned in error strings.
- **SDS secret namespace boundary** — all downstream/upstream TLS secrets are derived from already-validated IR `TLSCertificate`/`TLSCACertificate` structs; the SDS layer (translator.go:1080-1186, listener.go:984-1026) just embeds bytes inline. Namespace enforcement happens upstream in the gateway-api translator.
- **OIDC HMAC secret** — generated via `crypto/rand.Read` of 32 bytes (certgen.go:299-313). Length and source acceptable.
